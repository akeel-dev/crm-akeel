| N1 | `ci.yml`, bloco `on:` | `push:` sem filtro de branch junto com `pull_request:` faz um PR aberto de um branch do próprio repositório rodar o CI duas vezes. O `concurrency` não evita isso, porque os refs diferem (`refs/heads/x` e `refs/pull/N/merge`). Custa minutos de runner e não tira correção. Evidência: o próprio arquivo, linhas 5–7 e 12–14. | baixa | não |
| N2 | `Dockerfile`, os dois `FROM` | As actions estão fixadas por SHA, mas as imagens base estão fixadas só por tag (`node:24.22.3-alpine3.24`, `nginxinc/nginx-unprivileged:1.30.6-alpine3.24`), e tag pode ser republicada. A spec e o ADR não exigem digest (grep por `digest`/`sha256` no ADR 0001: nada sobre imagens). Fica a assimetria de rigor dentro do mesmo commit. | baixa | não |
| N3 | `Dockerfile`, estágio final (`USER 101`, `EXPOSE 8080`) | Ponytail: as duas linhas repetem o que a base já declara (o comentário do próprio Dockerfile diz "a imagem base já roda como o usuário nginx (uid 101) e escuta na 8080"; `docker history` mostra o `USER 101` da base). O `USER` explícito tem uma defesa: protege o critério 4 se a base mudar. O `EXPOSE` não tem. | baixa | não |
| N4 | story 0-15, "Como verificar" × critério 2 | Fato divergente entre artefatos, do Planejador. O critério 2 exige o passo de lint, mas o "Como verificar" é `npm ci … && npm test && npm audit --audit-level=high && npm run build`, sem `npm run lint`. Quem roda só o "Como verificar" não mede o critério 3 para o lint. Rodei à parte: LINT_EXIT=0. | baixa | não |

Observações que não são achados:
- O runner faz `npm ci` e `npm run build` duas vezes: nos passos do workflow e dentro do `docker build`. A duplicação vem da story, porque o critério 2 pede o build e a imagem como passos separados.
- O `location /assets/ { try_files $uri =404; }` vai além do texto do critério 4 ("qualquer rota desconhecida da SPA"). Arquivo de build inexistente não é rota da SPA, então o 404 é coerente com o critério, e não excesso.
- O workflow fecha o N3 de `reviews/0-14.md`: o lint agora roda em todo push.
