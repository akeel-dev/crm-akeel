# Story 0-04 — O par back+front sobe numa homologação local pelo mesmo caminho do deploy

Dono: Planejador. Congela quando o primeiro papel é despachado; depois disso, achado vai
para `conflitos/`.

**Onda:** 0 · **Repositório:** raiz (um commit)
**Requisitos da spec:** §4.5, passos 4 e 5 do pipeline (homologação + e2e; produção com aprovação manual, Flyway como etapa própria, depois troca das instâncias), RNF-13 (migração antes da troca), RF-SEC-03; ADR 0001, decisões 2 (manifesto de deploy, contrato OpenAPI) e 7 (deploy no `.github/` do raiz); `decisoes/2026-11-24.md §10`
**Rigor:** leve
**Depende de:** 0-07 (imagem do backend), 0-10 (modo `migrate`), 0-15 (imagem do frontend), 0-20 (o e2e que o passo 4 roda), 0-03 (série no raiz)
**Bloqueada por:** — para a verificação local. A execução **real** no GitHub e na VPS depende do remoto do raiz, do acesso à VPS e dos segredos (pendências da onda); esta story **não** depende deles para passar.

## Objetivo

O deploy existe como código e roda localmente:

- um **manifesto** em `deploy/` fixa a tag da imagem do backend e a do frontend que sobem
  juntas (ADR 0001, decisão 2);
- um script de deploy, parametrizado pelo ambiente, faz **migração Flyway como etapa
  própria** (o backend no modo `migrate`, de 0-10) e só depois sobe `api`, `worker` e o
  frontend;
- o workflow do raiz (`.github/workflows/`) chama esse mesmo script: homologação + e2e
  (passo 4) e produção com **aprovação manual** (passo 5, `environment` protegido), mais a
  comparação do contrato OpenAPI (`cmp`).

## Critério de aceite

1. **Dado** o manifesto com duas tags construídas localmente (por 0-07 e 0-15), **quando** se
   roda o script de deploy para o ambiente `homologacao-local`, **então** a ordem observada
   no log é: migração termina com sucesso → `api` e `worker` sobem → frontend sobe; e a
   SPA responde pelo mesmo endereço de origem que a API (o cookie da BFF depende disso).
2. **Dado** uma migração que falha (sabotagem: uma migração inválida numa tag de teste),
   **quando** o script roda, **então** ele para antes de trocar as instâncias, e as
   instâncias que estavam de pé continuam respondendo. Sabotagem registrada e desfeita.
3. **Dado** a homologação local de pé, **quando** o script roda o e2e de 0-20 contra ela,
   **então** o e2e passa.
4. **Dado** os workflows do raiz, **quando** se roda o actionlint por contêiner
   (`docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:latest`), **então** sai com 0.
5. **Dado** o workflow de produção, **quando** se lê, **então** o job de produção exige
   aprovação manual (`environment` com revisores) e **só** chama o script de deploy com as
   tags do manifesto; nenhum segredo aparece em claro, só `secrets.*` (RF-SEC-03).
6. **Dado** `backend/openapi/openapi.json` e `frontend/openapi/openapi.json` diferentes,
   **quando** o workflow do raiz roda o passo de contrato, **então** ele falha (é o mesmo
   `cmp` da `comandos.suite`).
7. **Dado** uma sessão fria, **quando** alguém lê `docs/operacao/deploy.md`, **então**
   encontra: como mudar as tags do manifesto, como rodar a homologação local e o que falta
   para o deploy real (remoto, VPS, segredos, Cloudflare Tunnel), como lista de pendências.
