**O realm.** O realm real é `crm`, em `https://akpannel.akeel.com.br` (spec §5.1). O realm
local de teste tem o **mesmo nome**, `crm`, e espelha o que a §5.1 e a §5.2 descrevem dele,
com dados fictícios. O nome vem de `KEYCLOAK_REALM`, nunca de valor fixo.

## Objetivo

`docker compose up -d --wait` na raiz sobe, saudáveis, os serviços de infraestrutura de
que as stories da onda precisam: PostgreSQL, Keycloak com o realm de teste `crm`,
Garage (S3) com bucket e chave criados, e Mailpit. A aplicação (back e front) **não** está
no compose: roda pelo `./mvnw` e pelo `npm` de cada repositório, apontando para estes
serviços.

## Critério de aceite

1. **Dado** uma máquina com Docker e sem volumes do projeto, **quando** se roda
   `docker compose up -d --wait`, **então** o comando sai com 0 e
   `docker compose ps --format json` mostra todos os serviços `healthy`.
2. **Dado** o compose de pé, **quando** se consulta o PostgreSQL (`SHOW server_version_num`),
   **então** o valor é `>= 170000` (D-05), e existem dois bancos separados: o do CRM e o do
   Keycloak (o Keycloak não usa H2).
3. **Dado** o Keycloak de pé, **quando** se lê
   `http://localhost:<porta>/realms/${KEYCLOAK_REALM}/.well-known/openid-configuration`
   (localmente, `.../realms/crm/.well-known/openid-configuration`), **então** a
   resposta é 200, e o realm importado tem os clientes da §5.1:
   - `crm-bff`: **confidencial**, Authorization Code com PKCE `S256` obrigatório, redirect
     e `post_logout_redirect_uri` só para `http://localhost:*` (é o cliente de login, P-18),
     o que cobre o callback `http://localhost:5173/login/oauth2/code/keycloak` (pelo proxy
     do Vite) e o da homologação local; "Backchannel logout URL" e "Front-channel logout
     URL" **vazias**, como no real (ADR 0003, emenda §15, item 2);
   - `crm-api`: confidencial, só `client_credentials` (conta de serviço), sem fluxo de
     navegador;
   - `crm-web`: **público**, PKCE `S256`, só para paridade com o real. Nenhuma story da
     Onda 0 faz login por ele;
   - o segredo de cada cliente confidencial **não** está no JSON: entra por substituição de
     variável na importação, a partir do segredo local (critério 6);

   e também:
   - os grupos `/Perfis/Administradores`, `/Perfis/Gestores`, `/Perfis/Vendedores`,
     `/Perfis/Visualizadores` e pelo menos um `/Equipes/*` (ex.: `/Equipes/Comercial`);
   - `preferred_username` igual ao e-mail (mapper ou "e-mail como nome de usuário" do
     realm), e os claims `roles` e `groups` como a §5.1 os descreve (pela P-19, o CRM não os
     usa para autorizar; existem para o token local ter a forma do real);
   - pelo menos três usuários fictícios: um `@akeel.com.br` com e-mail verificado, um
     `@akeel.com.br` com e-mail **não** verificado e um de outro domínio (são os casos de
     0-09 e 0-20). O verificado fica num grupo `/Perfis/*` e num `/Equipes/*`;
   - nenhum provedor Google configurado (login com Google é configuração da TI no real).
4. **Dado** o Garage de pé, **quando** o script de inicialização termina, **então** existe
   um bucket do CRM e uma chave com acesso a ele, e as credenciais estão num arquivo de
   segredo local ignorado pelo git, não no `compose.yaml`.
5. **Dado** o Mailpit de pé, **quando** se envia um e-mail SMTP para ele, **então** ele
   aparece na API do Mailpit (RF-NOT-09).
6. **Dado** o repositório, **quando** se procura senha, chave ou segredo de cliente no
   `compose.yaml` e em `deploy/**`, **então** só aparecem referências a arquivos de segredo
   do Docker (`secrets:`) e um `*.example` com valores fictícios. Um script de primeira
   execução gera os segredos locais a partir do exemplo (RF-SEC-03).
7. **Dado** `docker compose down -v` seguido de `up -d --wait`, **quando** termina, **então**
   o estado é o mesmo do item 1 (o ambiente é reprodutível do zero).
8. **Dado** uma sessão fria, **quando** alguém lê `docs/operacao/ambiente-local.md`,
   **então** encontra as portas, as credenciais fictícias de cada usuário de teste, como
   rodar o backend e o frontend contra este ambiente e como zerar tudo; e também:
   - que a SPA e a BFF são vistas na **mesma origem** (`http://localhost:5173`): o proxy do
     Vite (0-19) manda `/api/`, `/oauth2/authorization/`, `/login/oauth2/code/` e `/logout`
     ao backend, mantendo o `Host`; o resto é da SPA;
   - como rodar, **à mão**, contra o Keycloak **real**: `KEYCLOAK_CLIENT_ID=crm-bff-dev` e o
     segredo exportado na shell como `KEYCLOAK_CLIENT_SECRET` (nunca em arquivo versionado,
     nem `.env` no repositório); e que **nenhum teste automatizado** usa o Keycloak real,
     só o deste compose ou o de Testcontainers.
9. **Nenhum nome de realm fixo.** **Dado** `compose.yaml`, `deploy/local/**` e
   `deploy/keycloak/**`, **quando** se procura o nome do realm, **então** ele só aparece
   como valor de `KEYCLOAK_REALM` (no `*.example`/`.env` local, com `crm` como valor) e
   dentro da própria exportação `realm-crm-local.json`; o compose e o `verificar.sh`
   leem `KEYCLOAK_REALM`. Prova por presença: rodar o `verificar.sh` com `KEYCLOAK_REALM`
   apontando para um nome inexistente faz o critério 3 falhar (registrada no Registro).

## Como verificar

```
docker compose down -v && docker compose up -d --wait && sh deploy/local/verificar.sh
```

`deploy/local/verificar.sh` (do DevOps) faz, e falha no primeiro erro: os critérios 2, 3
(well-known do realm de `KEYCLOAK_REALM` + presença dos três clientes com o tipo certo, dos
grupos e dos três usuários, pela Admin API local), 4
(lista o bucket com a chave) e 5 (envia e lê de volta no Mailpit). O critério 9 é por
leitura do Revisor mais a prova por presença registrada pelo DevOps.

## Fora desta story

- **Gotenberg.** O ADR o lista no compose, mas nenhuma story da Onda 0 gera PDF. Versão mais
  barata (Ponytail): fica de fora. *Depois, se:* começar a onda de propostas (PRP).
- O Garage de **destino** do teste de backup (0-03).
- PostgreSQL com pgBackRest e arquivamento de WAL (0-03 troca a imagem).
- O backend e o frontend dentro do compose (a homologação local de 0-04 faz isso).
- **O roteamento do mesmo domínio** (os quatro prefixos da BFF para a `api`, o resto para
  a SPA, com `Host` e `X-Forwarded-Proto` repassados; ADR 0003, emenda §15, item 3): este
  compose não tem a aplicação nem proxy. É de 0-04 (proxy da homologação local, crit. 8 e
  9) e de 0-19 (proxy do Vite em desenvolvimento, crit. 8). Aqui só o documento o descreve
  (critério 8).
- Login com Google, MFA, limite de tentativas de login (RNF-08): configuração do realm real
  `crm`, da TI.
- `crm-web-dev`: não espelhado; o CRM não faz login por cliente público (P-18).
- A sincronização do grupo `/Perfis/*` pelo CRM, via Admin API com o `crm-api`: Onda 1,
  módulo IAM (spec §5.2 RF-IAM-02 e §14.1 P-19).
