## Objetivo

`docker compose up -d --wait` na raiz sobe, saudáveis, os serviços de infraestrutura de
que as stories da onda precisam: PostgreSQL, Keycloak com um realm `sed` de teste,
Garage (S3) com bucket e chave criados, e Mailpit. A aplicação (back e front) **não** está
no compose: roda pelo `./mvnw` e pelo `npm` de cada repositório, apontando para estes
serviços.

## Critério de aceite

1. **Dado** uma máquina com Docker e sem volumes do projeto, **quando** se roda
   `docker compose up -d --wait`, **então** o comando sai com 0 e
   `docker compose ps --format json` mostra todos os serviços `healthy`.
2. **Dado** o compose de pé, **quando** se consulta o PostgreSQL (`SHOW server_version_num`),
   **então** o valor é `>= 170000` (D-05), e existem dois bancos separados: o do CRM e o do
   Keycloak (o Keycloak não usa H2).
3. **Dado** o Keycloak de pé, **quando** se lê
   `http://localhost:<porta>/realms/sed/.well-known/openid-configuration`, **então** a
   resposta é 200, e o realm importado tem:
   - um cliente **confidencial** do CRM, fluxo Authorization Code com PKCE `S256`
     obrigatório, redirect só para `localhost` (§5.1);
   - pelo menos três usuários fictícios: um `@akeel.com.br` com e-mail verificado, um
     `@akeel.com.br` com e-mail **não** verificado e um de outro domínio (são os casos de
     0-09 e 0-20);
   - nenhum provedor Google configurado (login com Google fica para quando P-15 fechar).
4. **Dado** o Garage de pé, **quando** o script de inicialização termina, **então** existe
   um bucket do CRM e uma chave com acesso a ele, e as credenciais estão num arquivo de
   segredo local ignorado pelo git, não no `compose.yaml`.
5. **Dado** o Mailpit de pé, **quando** se envia um e-mail SMTP para ele, **então** ele
   aparece na API do Mailpit (RF-NOT-09).
6. **Dado** o repositório, **quando** se procura senha, chave ou segredo de cliente no
   `compose.yaml` e em `deploy/**`, **então** só aparecem referências a arquivos de segredo
   do Docker (`secrets:`) e um `*.example` com valores fictícios. Um script de primeira
   execução gera os segredos locais a partir do exemplo (RF-SEC-03).
7. **Dado** `docker compose down -v` seguido de `up -d --wait`, **quando** termina, **então**
   o estado é o mesmo do item 1 (o ambiente é reprodutível do zero).
8. **Dado** uma sessão fria, **quando** alguém lê `docs/operacao/ambiente-local.md`,
   **então** encontra as portas, as credenciais fictícias de cada usuário de teste, como
   rodar o backend e o frontend contra este ambiente e como zerar tudo.

## Como verificar

```
docker compose down -v && docker compose up -d --wait && sh deploy/local/verificar.sh
```

`deploy/local/verificar.sh` (do DevOps) faz, e falha no primeiro erro: os critérios 2, 3
(well-known + presença do cliente e dos três usuários), 4 (lista o bucket com a chave) e
5 (envia e lê de volta no Mailpit).
